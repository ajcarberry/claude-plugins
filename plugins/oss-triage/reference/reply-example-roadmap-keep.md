Thanks for thinking this through from the small-studio perspective. The cost pressure you are describing is definitely real.

The direct answer to your question: No, every new client does not have to download the fragments from the central server. We absolutely envision server caches and edge-caches that can proxy data and minimize network and data egress costs. Cache nodes and edge servers are on the roadmap. But clients serving each other is a stated non-goal: Lore is centralized by design, and clients talk to the remote rather than to each other; the [system design doc](https://epicgames.github.io/lore/explanation/system-design/#32-explicit-non-goals) lists peer-to-peer decentralization as an explicit non-goal, and [section 14.1](https://epicgames.github.io/lore/explanation/system-design/#141-why-centralized) explains our view as to why a symmetric peer model would be a very different kind of system.

The roadmap item that goes after this problem space is [Edge instances and advanced server topologies](https://epicgames.github.io/lore/roadmap/#edge-instances-and-advanced-server-topologies) (2027, Exploring). Its stated goal is to iterate on and optimize server replication for the most extreme cases, so Lore stays fast no matter how far a project reaches. The design already describes edge servers that sit near a group of clients and serve most fragment reads from a local cache, only going upstream on a miss ([System design, 21.4](https://epicgames.github.io/lore/explanation/system-design/#214-hotwarmcold-tiering-and-edge-servers)). Our initial view is that we want to offer the self-hostable cache mechanism you are suggesting, one benefit of which would be to minimize network and data egress costs. Potentially that extends to self-hostable local caches for Lore servers you do not own or administer yourself, UEFN being an obvious example.

What exists today: multi-server deployments are supported. Servers in a region replicate fragments and branch state to each other, and a `[topology]` setting tells a server how to find its peers ([21.5](https://epicgames.github.io/lore/explanation/system-design/#215-replication-failover-and-read-replicas), [topology settings](https://epicgames.github.io/lore/reference/lore-server-config/#topology-settings)). A server can also run a local cache tier in front of durable storage such as S3 (the `composite` store mode), so a read only goes back to S3 when the fragment is not already cached on the server, and cold content is rehydrated on demand ([21.4](https://epicgames.github.io/lore/explanation/system-design/#214-hotwarmcold-tiering-and-edge-servers)). 

So: clients serving other clients is not a goal, but the flexible topology and cache node parts of your suggestion are very much on our roadmap, and the growth path you sketch, one small server first and dedicated caches later, is the one we have in mind.
