# Slack summary to engineering, posted 2026-09-17 (final, as sent)

Did a triage pass on the public Lore issues yesterday. Went through about 20, closed most of them (fixed, duplicates, junk, already-documented). A few things came out of it worth sharing:

[Issue#208](https://github.com/EpicGames/lore/issues/208) - Docker Hub recently stopped serving minio/minio, and the integration compose file was still pointing at it, so integration tests were broken. [PR#206](https://github.com/EpicGames/lore/pull/206) just landed to switch to Quay, but @Connor Sidwell just posted [PR#214](https://github.com/EpicGames/lore/pull/214) to switch to RustFS, which would be a more robust solution given the direction the MinIO project has chosen. 

[Issue#200](https://github.com/EpicGames/lore/issues/200) - The commits tagged v0.8.5 and v0.9.0 both have a stale workspace version in Cargo.toml, so anyone building from the tagged revision gets a nightly string (v0.9.0 reports `0.8.7-nightly+0`), and bug reports come in with misleading versions ([Issue#181](https://github.com/EpicGames/lore/issues/181) is one). I see that Cargo.toml went 0.9.1-nightly to 0.10.1-nightly today without ever holding a bare 0.10.0, so the v0.10.0 tag about to be cut will likely repeat it. Is bumping the workspace version part of the tagging procedure? @Valentin

[Issue#199](https://github.com/EpicGames/lore/issues/199) - We don't declare a minimum Rust version. v0.9.0 apparently needs 1.93 or newer (?), and its not documented or defined anywhere. Ubuntu 22.04, 24.04, and Debian stable all ship older rust versions, so they get a raw compiler error after most of the workspace has compiled. And since the prebuilt binaries don’t currently run on Ubuntu 22.04 ([Issue#143](https://github.com/EpicGames/lore/issues/143), glibc 2.39), building from source is the practical route for many people. Seems like a beneficial 1 line change, but do we want to commit to defining a minimum Rust version?

[Issue#143](https://github.com/EpicGames/lore/issues/143) - Related: our prebuilt Linux binaries currently require glibc 2.39, so they don't run on Ubuntu 22.04 (which is still LTS till mid next year, and the WSL2 default for a lot of people). Not necessarily a bug, but we don't have an intentional support floor documented anywhere. Do we want to state "24.04 or newer" in the install docs, or build on an older baseline?

[PR#82](https://github.com/EpicGames/lore/pull/82) - Now that `main` ships a portable aarch64 build by default, with the tuned Neoverse path as an opt-in, there has been a community proposal to add a small addition on top: check `/proc/cpuinfo` for SVE2 before applying the tuned flag to the rpmalloc build, and warn and fall back to portable if it's missing. It protects a self-compiler who opts into the tuned build on the wrong hardware from a silent SIGILL. Small change, but seems valuable. Do we want to incorporate it, or should we ask him to close it? @Raghav.

[Issue#92](https://github.com/EpicGames/lore/issues/92) - I experienced an interesting testing pattern used by the reporter where they replayed a real Blender project's full git history into Lore commit by commit and shipped it as a re-runnable kit. Ninety-six sequential commits of a real production repo, including large binary assets, with stage, commit, and push against a live local server at every step. It’s a testing shape that own tests don't currently cover and it uncovered something that our tests didn't catch. Was thinking it might be worth borrowing the approach. :shrug

FYI - [Issue#91](https://github.com/EpicGames/lore/issues/91) - madskristensen built a Visual Studio extension for Lore ([LoreVS](https://github.com/madskristensen/LoreVS), Apache-2.0, last release Sept 2). Looks pretty cool. Just wanted to share another community project that building on Lore and our official .NET SDK (LoreVcs 0.8.3 from NuGet, run in a .NET 9 worker process and called over JSON-RPC). Worth noting he had to run the SDK out of process because it targets .NET 9 only; if we care about VS extensions or Unity editor tooling, a .NET Standard 2.1 compatible target would remove that hurdle.
